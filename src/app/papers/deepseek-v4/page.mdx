# DeepSeek-V4：高效百万上下文智能

DeepSeek-V4 的核心问题不是“上下文窗口能不能标到 1M”，而是：当上下文真的达到百万 token 时，模型还是否能以可承受的 FLOPs、KV cache、训练样本和后训练成本保持智能。报告把这个问题拆成架构效率、优化器、长上下文训练和后训练四部分，其中最值得放进 OPD 脉络里的是一句非常明确的设计：**mixed Reinforcement Learning stage was entirely replaced by On-Policy Distillation**。<Cite n={1} />

> 📌 前置：建议先读 [DeepSeek-V3.2](/papers/deepseek-v3-2)、[OPD 总览](/papers/opd-agarwal)、[GLM-5](/papers/glm-5)。V3.2 重点是稀疏注意力与大规模 GRPO，V4 则把百万上下文效率和 full-vocabulary OPD 放到同一条系统路线里。

## 一、动机：1M 上下文贵在哪里

长上下文能力不是简单把 RoPE 拉长。百万 token 规模会同时放大四类成本：

1. **prefill 计算**：输入越长，注意力与前向计算越贵；
2. **KV cache**：解码时要长期保存上下文状态，显存压力快速上升；
3. **训练样本**：长文档、长代码仓库、长程任务很难构造高质量监督；
4. **后训练 rollout**：如果用 RL 做长上下文任务，每条轨迹都可能非常昂贵。

DeepSeek-V4 的问题意识是：百万上下文只有在成本同步下降时才有意义。<Cite n={1} />否则它只是论文数字，无法成为真实产品能力。

## 二、模型规格：Pro 与 Flash 的双路线

报告给出两条模型路线：<Cite n={1} />

| 模型 | 总参数 | 激活参数 | 目标 |
|---|---:|---:|---|
| DeepSeek-V4-Pro | 1.6T | 49B | 高能力百万上下文模型 |
| DeepSeek-V4-Flash | 284B | 13B | 更低成本的高效部署模型 |

两者都支持 1M context。报告称，V4-Pro 在 1M context 下相对 DeepSeek-V3.2 只需要约 **27% single-token inference FLOPs** 和 **10% KV cache**。<Cite n={1} />这说明 V4 的重点不是单点 benchmark，而是把长上下文的单位成本压下来。

这条路线和 [DeepSeek-V3.2](/papers/deepseek-v3-2) 是连续的：V3.2 证明稀疏注意力可以服务长上下文和 RL 扩展；V4 则进一步把百万上下文变成端到端效率工程。<Cite n={[1,2]} />

## 三、架构：CSA + HCA 混合注意力

DeepSeek-V4 报告中的注意力路线可以理解为“不是所有 token 都值得全量互看”。<Cite n={1} />长上下文里，大量 token 只提供局部背景或可稀疏检索的信息，少数位置才需要全局聚合。

报告提到的 CSA + HCA 混合注意力，正是在这个前提下组织计算：<Cite n={1} />

| 机制 | 直觉 | 解决的问题 |
|---|---|---|
| CSA | 用更低成本处理长序列中的主要上下文 | 降低百万 token 下的注意力 FLOPs |
| HCA | 保留必要的全局或高价值上下文交互 | 避免稀疏化后丢失关键证据 |
| 混合结构 | 把局部、稀疏和全局能力组合 | 在效率与长程推理质量之间折中 |

长上下文模型最怕两种极端：全量注意力太贵，过度稀疏又找不到证据。V4 的工程目标就是在这两者之间找到可训练、可推理、可部署的中间形态。

## 四、优化器与训练：mHC、Muon 与稳定效率

百万上下文不只考验模型结构，也考验优化器和训练稳定性。报告把 mHC 与 Muon 放进核心技术栈，说明 DeepSeek-V4 延续了近两年大模型训练的趋势：优化器不再是附属超参，而是系统能力的一部分。<Cite n={1} />

对长上下文模型来说，优化器至少影响三件事：

1. 长序列训练中的数值稳定；
2. 稀疏注意力和 MoE 路由下的梯度质量；
3. 训练吞吐与收敛速度的平衡。

如果说 DeepSeek-V3 的看点是 FP8 与 MoE 工程，V3.2 的看点是 DSA 与 GRPO，那么 V4 的看点就是把长上下文架构、优化器和后训练蒸馏作为一个整体优化。

## 五、在线蒸馏：为什么替换 mixed RL 阶段

DeepSeek-V4 报告明确写到：后训练中的 mixed RL 阶段被 **On-Policy Distillation（OPD）** 完全替换。<Cite n={1} />这是很强的信号：在 V4 的目标任务里，继续混合 RL 的性价比不如让强老师在学生状态上提供密集监督。

它的 OPD 目标可以概括为：

$$
\mathcal{L}_{\mathrm{OPD}}(\theta)
= \sum_i w_i \cdot D_{\mathrm{KL}}\left(\pi_\theta \Vert \pi_{E_i}\right)
$$

其中 $E_i$ 可以理解为不同老师或专家策略，$w_i$ 是对应权重。这个形式和 [OPD 总览](/papers/opd-agarwal) 里的 MOPD 思路一致：不是把一个老师答案离线塞给学生，而是在学生自己的状态上，让多个老师提供分布级目标。<Cite n={[3,4]} />

对 DeepSeek-V4 来说，OPD 可能解决的是三个后训练矛盾：

1. **长上下文 RL 太贵**：每次 rollout 都长，最终奖励又稀疏；
2. **多能力合并困难**：代码、长文档、推理、agent 等老师可能各自擅长不同领域；
3. **部署模型需要稳定**：Flash / Pro 都需要把能力压进目标模型，而不是线上依赖多模型路由。

## 六、full-vocabulary OPD 与 teacher scheduling

很多 OPD 实现为了省成本，只看 teacher top-k 分布或 sampled token。但 DeepSeek-V4 报告提到 **full-vocabulary OPD** 与 efficient teacher scheduling，说明它关注的是更完整的分布对齐。<Cite n={1} />

full-vocabulary OPD 的优势是信号更完整：学生不仅知道老师最喜欢哪些 token，也知道整张分布的相对形状。<Cite n={[1,4]} />代价是老师打分和通信都更贵，尤其在百万上下文或大 batch 场景中。

因此 teacher scheduling 很关键：

| 问题 | 如果不调度 | 调度要解决什么 |
|---|---|---|
| 多老师成本 | 每个样本都问所有老师，成本爆炸 | 只在需要的样本 / 领域上调用合适老师 |
| 长上下文吞吐 | full-vocab logits 体积很大 | 控制 teacher 频率与批处理方式 |
| 能力冲突 | 不同老师给出不同偏好 | 用权重或 routing 管理监督来源 |

这让 DeepSeek-V4 的 OPD 更像一个后训练系统，而不是一个单独 loss。<Cite n={1} />

## 七、和 GLM-5、MiMo-v2-Flash 的对照

DeepSeek-V4、[GLM-5](/papers/glm-5)、[MiMo-v2-Flash](/papers/mimo-v2-flash) 都在处理同一个大问题：如何把强能力稳定压进可部署模型。<Cite n={[1,4]} />

| 模型 | 主问题 | OPD / 蒸馏角色 |
|---|---|---|
| DeepSeek-V4 | 百万上下文效率与长程智能 | 用 OPD 替换 mixed RL，调度多老师 / full-vocab 信号 |
| GLM-5 | 长程 agentic engineering | 用在线蒸馏稳定迁移和恢复长程 agent 能力 |
| MiMo-v2-Flash | Flash 模型的推理效率 | 用 MOPD 吸收多领域老师的 dense token-level rewards |

共同趋势很清晰：RL 仍然重要，但在已有强老师、长轨迹昂贵、多领域能力需要合并时，OPD 正在成为更可控的后训练工具。<Cite n={[1,4]} />

## 八、局限：百万上下文仍然难评估

DeepSeek-V4 的路线值得关注，但读它时要保留几个限制：

1. **1M context benchmark 不等于真实工作流**：needle、长文档 QA 和真实代码仓库任务差异很大。
2. **稀疏机制可能转移成本**：注意力省下的成本，可能转移到索引、路由、缓存或数据管线。
3. **full-vocabulary OPD 成本高**：teacher logits 的存储、传输与调度可能成为瓶颈。<Cite n={4} />
4. **teacher 依赖强**：OPD 的上限很大程度取决于 teacher pool 的质量和互补性。
5. **系统细节不可完全复现**：百万上下文训练和后训练的工程栈比单个 loss 更重要。

## 小结

DeepSeek-V4 的价值在于把百万上下文从“窗口长度竞赛”推进到“单位成本智能”的问题上。CSA + HCA、mHC、Muon 和 MoE 负责降低长上下文建模成本；OPD 则负责把长程能力、多老师能力和后训练策略压回目标模型。它说明在线蒸馏已经不只是数学推理上的省钱技巧，而是前沿长上下文模型后训练系统的一部分。
